Become a validator

Funded validator admission — registering a new validator by bonding your own BLCH from existing UTXOs — is specified, implemented, and merged. It is not activated on mainnet. This page tells you exactly what stands between here and a joinable network, what you can genuinely prepare today, and the precise procedure for the day the gate opens.

Implemented, not activated

The consensus flag day is unarmed: FUNDED_VALIDATOR_ADMISSION_ACTIVATION_EPOCH = u64::MAX. Every mainnet node refuses FundedDeposit transactions today, and no runtime option changes that. Merging prepared the door; it did not open it.

The gates, in order

Before anyone can join as a validator, all four of these must happen. Each is a hard dependency, not a formality:

  1. Weak-subjectivity checkpoint published. Since 2026-09-05 a fresh node cannot sync mainnet at all (see Run a node); the signed checkpoint plus the signer-set ceremony must ship first. Status: not shipped.
  2. Coordinated release + flag day. A finite admission epoch changes block validity; it must be agreed, published, and every validating node rebuilt onto the same release before that epoch arrives. No runtime option enables it. Status: no epoch agreed or published.
  3. Exit/withdrawal lifecycle. The spec states plainly that this work does not activate authenticated exits, withdrawals, slashing evidence, or RANDAO recommit — those have their own unarmed gates. In the spec's words:
    Admission must not be opened for public funds until the operator-approved lifecycle and those existing release dependencies are resolved. Otherwise bonds have no activated withdrawal path.
    Status: exit/withdrawal path not activated.
  4. Public P2P entry. Today's mesh is a firewalled devnet transport with no public bootstrap; opening requires the production transport rollout. Status: not rolled out.

What you can do today is everything below under Prepare now — key ceremony, hardware, a following node, and a rehearsed draft.

The protocol

Everything in this section is consensus fact from the merged implementation — the spec is docs/specs/BLOCH-FUNDED-VALIDATOR-ADMISSION.md in the public repository.

FundedDeposit — wire tag 0x0B

  • Consumes 1–128 existing, strictly-ordered, distinct UTXOs owned by one funding key; creates the validator record, an activation-queue entry, and one change UTXO.
  • Input values come from committed state — no RPC parameter or genesis-offset allowance can manufacture a bond.
  • The legacy Deposit (0x02) and Delegate (0x04) tags remain refused.

Two role-separated PQ authorizations

One unsigned intent, two signatures over it, from two roles that may live on different machines and different keys:

  • FUNDING — the owner of the coins authorizes: the UTXOs, the stake, the validator identity, the withdrawal route, the change/refund script, and the fee budget.
  • POSSESSION — the operator proves control of the validator key and accepts the terms, including the RANDAO commitment and the commission.

Both signatures use the suite-1 envelope b1 0c 01 00 = ML-DSA-65 and Falcon-1024, each signature verifying both algorithms. Funding and validator keys may differ; there is no custodial coordinator.

The intent binds the SHA3-256 of the canonical genesis manifest plus an inclusive expiry epoch — anti-replay across networks and across time.

Bond bounds

Minimum bond25,000 BLCH (= 2,500,000,000,000 sat)
Per-validator maximummax(25,000 BLCH, 1% of active stake)
Commission0 – 10,000 basis points
ScopeNew-key registration only — not a top-up, not delegation

Conservation

The transaction balances exactly, by consensus rule:

sum(inputs)    = B + C + Fmax + T
change created = C + Fmax − Factual
charged        = Factual + T

where B is the bond, C the signed minimum change, Fmax the signed maximum base fee, Factual the base fee actually charged at inclusion, and T the tip. The refund always goes to the signed change script, never to a validator reward. Inclusion above the signed maximum base-fee rate is refused.

Activation queue

  • Ordered by (deposit epoch, pubkey hash).
  • Delay of ≥ 8 epochs before activation; at most 4 admissions per epoch.
  • Registration queues — it does not grant consensus weight.

Signing roots

intent_root      = SHA3-256("BLOCH:VALIDATOR:DEPOSIT:V1"    || fields 1–8)
funding_root     = SHA3-256("BLOCH:VALIDATOR:FUNDING:V1"    || intent_root)
possession_root  = SHA3-256("BLOCH:VALIDATOR:POSSESSION:V1" || intent_root)
txid             = SHA3-256(DS_TXID || intent_root)   // existing rule; witness-independent

Prepare now

None of the gates above stop you from doing the slow, careful work today. A candidate who has done these four things joins on activation day; one who has not, waits.

  1. Hardware. Linux x86-64, 2+ vCPU, 8 GB RAM, 80 GB SSD — the same footprint as an observer node.
  2. Build from the public source. The exact clone / checksum / gunzip / build steps are in this portal's Run a node section — they are identical for a validator candidate.
  3. Offline key ceremony. Generate the validator keystore offline; keep the sealed keystore, the RANDAO seed, and the withdrawal-authority backups secure and separate. The withdrawal script must name a PQ key the intended recipient actually controls — registration does not establish that control. keygen --index auto exists for rehearsal only (devnet-grade).
  4. Run a following node now (observer posture), so your infrastructure is proven before your money is at stake. This is blocked today only by the weak-subjectivity checkpoint gate above.

The step-by-step at activation

This is the full procedure, verbatim from the spec. Steps 1–3 and 6 can be rehearsed today; step 4 only works once a finite admission epoch is live.

1. Query admission state

getvalidatoradmission — an unarmed build answers active:false, activation_epoch:null, plus the network domain, head epoch, stake bounds, queue limits, and next base fee. Fee and bound figures are quoted from the head; consensus rechecks them at inclusion.

2. Gather inputs and public material

listunspent for the funding authority; export the two suite-enveloped public keys as hex files, plus the RANDAO commitment from the offline ceremony. No private material enters the draft.

3. Prepare, inspect, and sign — each role on its own machine

bloch-pos validator-deposit prepare \
  --genesis genesis.bin \
  --funding-pubkey funding.pub.hex --validator-pubkey validator.pub.hex \
  --randao <commitment-hex32> --withdrawal <withdrawal-script-hex32> \
  --change <change-script-hex32> --stake 2500000000000 \
  --input <txid-hex32>:<vout>:<value-sat> \
  --max-base-fee <millisat-per-gas> --tip <millisat-per-gas> \
  --expiry <inclusive-epoch> --commission <basis-points> --out draft.hex

bloch-pos validator-deposit inspect --tx draft.hex
bloch-pos validator-deposit sign --tx draft.hex --role funding \
  --dir funding-keystore --out funded.hex
bloch-pos validator-deposit inspect --tx funded.hex
bloch-pos validator-deposit sign --tx funded.hex --role validator \
  --dir validator-keystore --out ready.hex
  • The passphrase comes from the sealed-keystore sourcing, never a command-line argument.
  • Inspect on each signing machine — network domain, inputs, validator hash, withdrawal script, commission, fee budget. Rebuilding any field invalidates both signatures.
  • --stake 2500000000000 is 25,000 BLCH expressed in sat — the minimum bond.

4. After activation: broadcast

Submit ready.hex via sendrawtransaction. The offline CLI never broadcasts anything itself.

5. Track

  • getvalidatorbykey <sha3-256 pubkey hash> — VALIDATOR_NOT_FOUND before inclusion is the ordinary pending state, not an error in your submission.
  • gettxstatus to distinguish included / justified / finalized.

6. Run the candidate node

Run with the auto-index keystore (the 4294967295 sentinel) and the correct genesis manifest. The node follows and verifies while queued and needs no restart when it becomes eligible; duties resolve the key from the committed registry, so there is no index race.

Operating notes

  • Never run one key twice. Doppelganger observation and the persistent slashing journal are on the signing path, bound to pubkey-hash + genesis digest (index-independent). The network permanently discards the fork-choice weight of an equivocating key — measured on this chain's own history, not a hypothetical.
  • Rewards and commission follow the existing emission schedule; queue and stake figures are live-queryable, not promises.
  • Rehearsal exists in-repo: scripts/rehearse-validator-admission.py copies the source, arms epoch 0 in the copy, runs the production paths end-to-end, and deletes the copy.
Honesty notes

The implementation, in the spec's own words, "has not received an independent cryptographic or consensus audit". Slashing evidence and exits have unarmed gates of their own — see the gates above and Security & disclosure.
